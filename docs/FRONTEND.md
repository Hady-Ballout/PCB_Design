### How the layout engine draws a human-readable schematic

`layoutCircuitDiagram(circuit)` turns the topological circuit model (components +
net connectivity, no coordinates) into a fully placed and routed diagram. The AI
never supplies positions; all geometry is deterministic. The pipeline aims to
read like an engineer drew it rather than a machine scattered parts:

1. **Rank into signal-flow columns.** `rankComponents` BFS-walks the net graph
   from the sources; a component's rank (distance in hops) becomes its column,
   giving left-to-right signal flow.
2. **Tidy placement first.** `buildDraft` places each rank's parts in that rank's
   vertical lane using `TIDY_GRID` — a single clean column per rank (ranks with
   several parts fan into a tight aligned block). This is the preferred, most
   hand-drawn-looking layout.
   - **Pin alignment.** Before placing a part, `alignmentRow` looks for an
     already-placed pin on a shared net and lines the part up with the row that
     pin escapes on, so series passives, op-amp inputs, and BJT bases connect in
     one straight run instead of a staircase. Alignment stays within the part's
     own rank band (long chains wrap into serpentine bands and must not collapse
     onto one endless row). Multi-pin side pins (op-amp inputs, BJT C/E) sit a
     grid multiple from the component center so aligned wires meet them without
     an off-grid jog at the pin.
   - **Upright grounded passives.** A grounded 2-pin part that flips vertical
     also swaps its body to portrait so the vertical zigzag glyph fits.
   - **Labels hug their part.** `makeComponentLabels` prefers spots just past
     the body box / pin-escape reach (26px above/below, 40px beside horizontal
     parts, 10px beside vertical ones); the outward ring search is a last
     resort, since text floating away from its part reads as machine layout.
3. **Route + validate.** `routeWithExpansion` runs the grid A\* router and
   `validateDiagramLayout`. The tidy pass gets a small expansion budget
   (`TIDY_EXPANSION_BUDGET`) so it bails quickly on topologies it can't route
   cleanly (e.g. an op-amp whose input parts rank to its right and must wrap
   around).
4. **Spread fallback.** If tidy can't route, retry once with `SPREAD_GRID` — the
   original wider fan-out that interleaves adjacent ranks enough to route dense
   feedback circuits. Only if *that* also fails does the server fall back to
   labeled-net stubs (`buildFallbackCircuitDiagram`).
5. **Local ground rail.** The ground net anchors just below the lowest grounded
   pin, so ground drops are short and clustered under their parts instead of
   routing the full height of the sheet.
6. **Crop to content.** On success, `cropDiagramToContent` trims the canvas to a
   tight box around the drawn geometry (resize-only, never moves a coordinate, so
   a validated layout stays valid) so the schematic fills its frame.

`toDiagramSvg` (in `pcbGenerator.js`) and the canvas (`CircuitDiagram.jsx`)
render pin-number labels only on multi-pin parts that need them (op amps,
generic symbols); two-pin passives are unnumbered the way a schematic normally
is, and BJTs rely on their C/B/E letters. The canvas draws wires, symbols,
junction dots, and bridge arcs in a single ink (`--color-text`), reserving the
accent color for hover/selection; net-label pills are invisible until
hovered/selected so net names read as plain text flags. Layout tuning constants
(`TIDY_GRID`, `SPREAD_GRID`, clearances, `CANVAS_MARGIN`) live at the top of
`schematicLayout.js`.

#### Slot grid and slot-anchored placement

Generated components are placed into a **fixed slot grid** rather than scattered
freely. The grid is the source of truth: `SCHEMATIC_SLOT_LAYOUT` (in
`schematicLayout.js`) fixes the slot size (`slotWidth`/`slotHeight`), `gap`,
`margin`, and column count; `slotCanvasSize(rows, cols)` *derives* the canvas
from the grid (the inverse of the old canvas-drives-slots relationship), and
`slotGridFor(count)` grows the row count so every component gets its own slot
(≥2 rows). All slot geometry lives in **core** (`slotRects`, `slotCenter`,
`assignSlots`, `nextFreeSlot`, `nearestSlot`) so the layout engine and the
renderer share one definition.

`layoutCircuitDiagram(circuit, { slots: true })` is the slot-placement mode:
`buildDraft`'s `slots` branch sizes the canvas from the grid, orders components
by signal-flow rank, assigns them column-major to slot cells (`assignSlots`), and
pins each component **exactly** at its slot center (bypassing the
collision-nudge). The existing A\* router then wires them through the gaps, and
external-terminal **ports** drop as short stubs beside their connected pin
(edge-anchored ports would be unroutable across fixed slots). The returned
diagram carries `slotLayout: { rows, cols }`; `cropDiagramToContent` never shrinks
below the slot-grid extent, so empty trailing slots stay visible. `buildCircuitDiagram`
(hence the server's generated diagram and every edit through `synchronizeResult`)
and the canvas **Auto-layout** button all use `{ slots: true }`.

`geometry.js` `addedComponent` drops a manually-added part into the
`nextFreeSlot`; **dragging stays unrestricted** (`movedComponent` is unchanged) —
snapping a drag into a slot is a later step, as is mapping a component's terminals
onto the slot pins. `preserveDiagramLayout` keeps user-dragged positions and grows
the canvas to contain them, so a part dragged past the grid is not shoved back.

The canvas draws the slots as dashed, numbered rectangles below the wires and
symbols. `schematicSlots(rows, cols)` in `geometry.js` wraps core's `slotRects`
and decorates each with the **fixed pin set** (`SCHEMATIC_SLOT_PINS`: `+`/`−`
signal pins on the left, `V+`/`V−` power rails on top/bottom) — always present so
a component that occupies a slot maps its terminals onto the pins it uses. The
renderer sizes the grid from `diagram.slotLayout` (falling back to
`slotGridFor(components.length)`); the layer is `pointerEvents="none"`.

## `src/app` — app shell

- **`App.jsx`** (~1200 ln) — the integration point. Owns: chat store state, active
  chat/circuit/SPICE/KiCad/JSON editor state, open editor windows + split-pane layout,
  canvas tool/selection state, generation streaming, simulation runs, and every
  synchronization effect that keeps SPICE/canvas/KiCad/JSON in agreement. Imports from
  `core` and every `features/*` module — nothing imports from `App.jsx`.
  - **Editor windows UI** — the workbench has no title/status header; the `editor-launchbar`
    sits flush at the top and renders as a minimalist browser-style tab strip (compact, no
    "Open views" label; open tabs read as connected to the content, the focused tab gets an
    accent underline). Each window titlebar has a **maximize/restore** control
    (`maximizedEditorView` state) alongside close: maximizing renders that window as a
    `position: fixed; inset: 0` overlay filling the **entire viewport** (hiding the split, chat
    panel and top bar), and while maximized, clicking another tab swaps the full-screen view
    (browser-tab behavior). Maximize state is in-memory only (not persisted).
  - **Two-phase prompt flow** — every submitted prompt runs `beginPrompt` (appends the user
    message, marks any stale pending clarification round as skipped, calls
    `/api/clarify-circuit` with a 20s abort timeout, and appends a pending
    `clarification` assistant message on success). Generation (`runGeneration`, the old
    `submitToChat` body parameterized on the prompt) only starts when the user answers or
    skips (`submitClarificationAnswers` → `composeClarifiedPrompt`), or immediately with
    the original prompt when the clarify call fails/returns no questions (silent
    fallback). `answerClarification` records chip/custom answers on the message.
    `generationBusy` covers both `generatingChatId` and the new `clarifyingChatId`;
    `isClarifying` drives a lightweight "Preparing a few quick questions…" bubble.
  - **Design-issue surfacing** — when the `complete` event carries error-severity `issues`
    (topology-rule findings; see `docs/AI_AND_CIRCUIT_MODEL.md`), the assistant message gets
    a "N design issue(s) remain — open the breadboard view" tail and the message stores
    `issues`; `circuitQualityIssues(result)` merges `result.issues` with the ERC
    `result.validation` and feeds the breadboard `IssuesPanel`. The generation catch path
    posts a soft "I couldn't produce a valid version of that request, so nothing was
    changed" chat message (workspace/SPICE restore unchanged) — with the server's
    best-candidate degrade, that path only fires when every attempt failed structurally.
- **`routing.js`** — `pageFromHash`, `AUTH_PAGES`, `PUBLIC_PAGES` (hash-based nav between
  home/login/signup/verify and the main workspace).
- **`generationStream.js`** — `readGenerationStream`, `markSpiceAsProvisional`: consumes the
  NDJSON stream from `/api/generate-circuit`.

`selectionModel.js` is the pure `highlightFor`/`readoutFor`/`pinLabelsFor` logic (unit-tested). **Navigation** is a pan/zoom canvas: the whole board sits in one `translate/scale` world `<g>` (fixed `viewBox` + `preserveAspectRatio`), dragging empty board pans, wheel/pinch zoom stays anchored under the cursor, two-finger trackpad pans, and gestures come through Pointer Events with `touch-action:none` (view transform is rAF-coalesced; the memoized `Breadboard` hole grid never re-renders during a gesture). `clientToViewBox`/`viewBoxToBoard` (in `breadboardGeometry.js`, mirroring `schematic/geometry.js`'s `svgPointer`) map pointer→board space. **Editing** (only when `App.jsx` passes the callbacks): with a part selected, its pins become drag handles — dragging a pin to another hole rewires it (resolved via `holeAt`+`netAtHole`, an empty hole disconnects to an `NC_*` placeholder), emitted as a targeted `component.nodes` edit through `onCircuitChange`→`applyCircuitChange`→`synchronizeResult` so SPICE/KiCad/JSON/schematic stay consistent; dragging a part body repositions it, persisted as an anchor in the `editedBreadboard` layer via `onLayoutChange`. `circuitToBreadboard(circuit, overrides)` honors those anchors in a two-phase placement (pinned parts first, greedy-around them second — byte-identical to pure auto-placement when no overrides), and `reconcileOverrides` drops anchors for removed parts. **Double-clicking the board** opens a browse-only **component library** popover (`ComponentLibrary.jsx`, `libraryAt` state) anchored at the cursor and clamped to the viewport: it lists every registry kind (`ALLOWED_KINDS`/`kindLabel` from `core/componentKinds.js`) grouped into Basic components / Sensors & modules / Boards (via `MCU_KINDS`/`WIRING_ONLY_KINDS`) with a search filter; each item previews its kind with **`PartThumbnail`** (`parts.jsx`) — the kind's *real* breadboard artwork rendered into a small standalone SVG from a per-kind spec table (synthetic holes for point-driven bodies, package meta for DIP/straddle bodies, a fake slot rect for off-board bodies, `BatteryPack` for sources; each thumbnail embeds its own `PartDefs`, and a `viewBox` crops the board-space region where that body draws) — this replaced the old `ComponentToolIcon` line glyphs and removed the library's cross-feature import of `schematic/symbols.jsx`, closing on Escape or backdrop click. Items stack in a **single column** (long labels ellipsize) so the list scrolls only vertically. **Picking an item adds that part** (`onSelect(kind)` → `addComponent` → `newComponentForKind`): it appends a fresh SPICE-safe-`ref` component with `DEFAULT_VALUE_BY_KIND` starter value and all pins as `NC_<REF>_<pin>` placeholders (mirroring the canvas's `addedComponent`), emitted through `onCircuitChange` so the board greedy-places it and its pins become drag-to-wire handles once selected; the popover then closes. When `App.jsx` passes no `onCircuitChange` (read-only view) the library is browse-only — items are `disabled` and never touch the circuit. Also: clickable net legend chips, pin labels on selection (kinds with a `fixedPins` contract — sensor modules, MCU boards, `timer_555`, `seven_segment` — pull their labels straight from the registry's `FIXED_PIN_NAMES`; manual entries cover opamp/comparator IN±/OUT, BJT C/B/E, MOSFET D/G/S, diode/zener/LED A/K, buzzer/dc_motor +/−, potentiometer A/W/B, switch_spdt A/COM/B, rgb_led R/G/B/K; label chips face away from the trench for any straddling package via `meta.columnStart`), a toolbar readout that also previews the hovered item while nothing is selected, +/−/Fit zoom controls, and SVG export via `downloadText`. Part labels carry a `paint-order` halo so crossing jumper wires don't strike through the text, and polarity is visible on parts: LEDs get a flat-sided lens on the cathode side, electrolytic cans a −-marked stripe plus a + shoulder glyph, and voltage sources draw as 9V snap-top battery packs (metal cap, female − ring and male + stud). **Issues panel** (`IssuesPanel.jsx`): a collapsible banner above the board (auto-open when errors exist) that finally surfaces circuit quality — `App.jsx` passes `issues` = the generation response's topology-rule findings (`data.issues`) merged with the server ERC (`data.validation`, previously computed and discarded), and the panel also folds in `model.integrity.issues` (board-level breaks) plus `model.warnings` (which replaced the old bare `.realistic-warnings` list). Rows are tagged by severity: red "Needs attention" (error), amber "Warning", green "Auto-fixed" (`autoFixed` violations repaired server-side), each with its message and concrete `fix` recipe. `circuitToBreadboard` itself now attaches `model.integrity = { ok, issues }` — a runtime SPLIT/SHORT self-check (`verifyBoardConnectivity`, the same union-find the debug description uses) plus placement-time errors: a net that can't be fully joined, a straddle package with the wrong node count drawn as a generic body (unreliable pin mapping), or a third supply that doesn't fit the rails. Silent jumper drops were eliminated at the source: nets tapped by ≥5 pins get promoted to a free power rail (what a human builder does), and jumper targets prefer tie groups with ≥2 free holes, bridging to a fresh relay column before a net's last hole is spent. A **"Copy description"** toolbar button (debug aid) copies a plain-text dump of the build — via `describeBreadboard(circuit, model)` in `breadboardDescription.js` (pure, unit-tested): intended netlist, per-net pin lists, physical placement (rails/batteries/parts/jumpers with breadboard hole addresses like `a5`), a reconstructed-connectivity check that flags any `SPLIT` (net across ≥2 nodes) or `SHORT` (node mixing nets), and warnings — so it can be pasted into an AI to verify the generated schematic (falls back to a downloadable `.txt` when the clipboard is unavailable). All four model files re-derive `isUnconnectedTerminal` locally rather than importing another chunk. **`BreadboardPreview.jsx`** is a static, non-interactive render of the same board — it runs `circuitToBreadboard` and reuses `Breadboard`/`RealisticPart`/`BatteryPack`/`JumperWire`/`PartDefs` with no pan/zoom/selection, fitting the SVG to its box via `preserveAspectRatio` — so other surfaces (e.g. the landing-page use-case cards) can embed the genuine generated board instead of a stand-in illustration. **Live simulation (Run mode)**: a **▶ Run / ■ Stop** toolbar toggle simulates the circuit in the browser via `src/core/sim` (see the `src/core` table) — no server, no Ngspice. `useSimulation.js` owns the engine in a ref, steps it in a `requestAnimationFrame` loop under a 4 ms/frame budget, and commits a small `simFrame` snapshot (`{time, speed, converged, netVoltages, observables, warnings, error}`) to React state every *other* frame (~30 Hz, the same coalescing idea as the view transform); control values (held button, thrown switch, wiper, sliders) live in a memory map keyed by ref so **editing the circuit while running rebuilds the engine seamlessly** with the user's control state replayed (`applyCircuitChange` flows through unchanged — sim time restarts). While running: LEDs draw a blurred glow halo (`rsGlow` filter in `PartDefs`) with log-scaled brightness from actual junction current, RGB lenses blend their three channel currents, 7-segment segments light individually, the pushbutton plunger depresses, the SPDT knob follows its throw, and the pot's cross-slot rotates with the wiper (−135°…+135°). Run-mode gestures replace part-drag (parts aren't movable while running): press-and-hold a pushbutton (`simButtonRef`, pointer-captured, released on pointerup/cancel), click-to-toggle kinds via the `RUN_CLICK_TOGGLES` table (SPDT throw, PIR motion — the Fresnel dome tints warm while triggered — and the hall sensor's magnet), drag a pot horizontally to sweep the wiper (60 board px = full sweep, `simPotDragRef`); selecting a part with slider controls (LDR light, thermistor/TMP36 °C, soil moisture, gas/sound level, pot precision) shows `SimStimulusPanel` range inputs. The toolbar shows a status chip (`live` for static circuits, `1.0×`/`0.4× (slow)` real-time speed for dynamic ones, `not converging` on NR failure), the readout and net-legend chips append live voltages/currents (`readoutFor(model, selection, simFrame)` — the optional third arg keeps old callers untouched), and a `.realistic-sim-banner` strip surfaces deduped engine warnings ("U1 (Arduino Uno) is not simulated — its pins float") or the fatal pre-flight error ("Connect the circuit to GND (net 0) to simulate"). **M3 sound & motion**: `simAudio.js` (`createSimAudio`) plays simulated buzzers through Web Audio — one square oscillator + gain per buzzer ref, created lazily inside the Run-click-initiated effect (autoplay-safe), gain ramped from |V| via `setTargetAtTime` (no pops), frequency from the engine's detected `freqHz` (2.4 kHz active-buzzer default for DC drive); the audio ref in `useSimulation` is keyed on `running` alone so mid-run circuit edits don't click the tone off. Motors animate: `DcMotorBody` spins a shaft cross-mark (`.rs-motor-spin`, `animationDuration` from `speed01`, `transform-box: fill-box`) and `VibrationMotorBody` jitters (`.rs-motor-shake`); the off-board dispatch in `RealisticPart` threads `sim` into the dc_motor slot body for this. **M4 polish**: a **"V map"** toolbar toggle (run mode only) tints every tie group and rail stripe by its live voltage — `voltageOverlayFor`/`voltageColor` in `selectionModel.js` build a `highlightFor`-shaped carrier map with explicit `groupKeyColors`/`railStripColors` (hue 220 blue at 0 V → hue 0 red at vMax) that `HighlightOverlay` prefers over the net-legend lookup, rendered beneath the selection highlight; blown fuses draw a broken element + smoked glass and label `· blown`; the relay module's indicator LED lights with a glow halo while energized; battery and jumper hover `<title>`s carry live values too. ## Persistence model

Everything user-facing is `localStorage`-backed (no server-side chat storage): the chat
store (`prompt-to-pcb-chats-v1`) and the editor split layout
(`prompt-to-pcb-editor-split-v1`). Per-chat persisted geometry lives on the chat record:
`editedDiagram` (schematic edits) and `editedBreadboard` (breadboard part-placement anchors,
`{ version, parts: { [ref]: { strip, column } } }`) — both survive reloads and are reconciled
against the circuit when topology changes. Only auth accounts live server-side (Postgres/Neon or an
in-memory fallback — see `docs/BACKEND.md`).
